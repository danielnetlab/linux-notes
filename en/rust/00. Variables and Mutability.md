## 00.01 How variables are created
A **variable** is a name associated with a value. It is created with `let`:
```rust
let x = 5; // x is called this way, its value is 5, Rust infers its type "i32"
```
---
## 00.02 Variable mutability
When creating a variable, **by default they are immutable**, which means they cannot be modified after declaration. This prevents:
- Weird bugs
- Hard-to-read code
- Security issues
```rust
let password = 5;
password = 6; // compile-time error because it is immutable
```
---
## 00.03 Mutability: allowing changes
To be able to change the value of a variable, it must be declared with `mut`. The variable is still the same one, but with a different value:
```rust
let mut x = 5;
x = 6; // compiles fine
```
Once the variable is declared, its value can be modified, but **not its data type**. The type is defined at declaration time and cannot be changed later.
```rust
let mut x = 5; // x is i32
x = 10; // compiles fine
x = 3.13; // ERROR because the type changes, you can’t switch to float
```
---
## 00.04 Compound assignment operators

|Operator|Expression|Meaning|
|---|---|---|
|`+=`|`x + 1`|add and reassign|
|`-=`|`x - 1`|subtract and reassign|
|`*=`|`x * 1`|multiply and reassign|
|`/=`|`x / 1`|divide and reassign|

When creating variables, they are used to perform mathematical calculations.
```rust
let mut x = 5;
x = x + 1; // long form
x += 1; // short form (same idea, more convenient)
```
---
## 00.05 Variable scope
It is the area of the code where a variable:
- exists
- is accessible
- is valid
In Rust, scopes are defined with **blocks** `{}`.
```rust
fn main() { // scope
    let x = 5;
    println!("{x}");
}
```
- `x` exists **only inside `main`**
- outside `main`, `x` does not exist
```rust
fn main() { // scope
    let x = 5;
    
    { // scope
        let y = 10;
        println!("{x} {y}");
    }
    
    println!("{x}");
    println!("{y}"); // error: it no longer exists here
}
```
---
## 00.06 When a variable stops existing
A variable:
- **is born** when it is declared
- **dies** when its scope ends
Rust strictly controls this to avoid:
- invalid memory access
- references to data that no longer exists
```rust
fn main() {
    let x = 5;
    
    {
        let x = 10;
        println!("{x}"); // 10
    }
    
    println!("{x}"); // 5
}
```
Here we see:
- there are **two different variables**
- each one lives in its own scope
- they don’t actually overwrite each other
---
## 00.07 Shadowing
It happens when you declare a variable with the same name as an existing one, causing the new variable to hide the previous one, making the old variable inaccessible from that point on.
```rust
let password = 5; // old value
let password = 6; // new value
```
### Real difference: `mut` vs shadowing
- With `mut`: you change the value of the same variable.
- With shadowing: you create a new variable and “cover” the previous one. You **can change the variable’s type**.
---
## 00.08 Basic lifetime (conceptual)
We won’t look at advanced lifetimes (`'a`) yet, but the idea is essential:
> **A variable lives as long as its scope is active.**

When the scope ends:
- the variable is destroyed
- its memory is freed
- it can no longer be used
This avoids errors such as:
- using data that no longer exists
- dangling references

## 00.09 turbofish
The **turbofish** (`::<>`) **explicitly specifies generic type parameters** when the Rust compiler cannot infer them automatically.
```rust
let x = "5";
let y = x.parse::<i32>();
```
---
## 00.10 Type inference vs explicit annotation
### Type inference
Rust automatically deduces a variable’s type. This works when:
- the value is clear
- there is no ambiguity
```rust
let x = 5;    // i32
let y = 3.14; // f64
```
### Explicit annotation
Sometimes **Rust forces you** to write the type:
```rust
const X: i32 = 5;
```
Or when there is ambiguity:
```rust
let n = "43".parse::<i32>();
```
---
## 00.11 Converting text to a number
A number in quotes is an **&str** (a reference to text). Rust does not allow operations between incompatible types due to its type system, which we’ll see later. Convert the text to the target type:
```rust
let user_age = "123";
let user_age = user_age.parse::<i32>();
```
It returns either a result or an error, which we’ll cover later.
```rust
let user_age = "apple";
let user_age = user_age.parse::<i32>(); // error
```
---
## 00.12 What `.parse()` really returns
`.parse()` returns a type called:
- `Result<T, E>`
Which means:
- **Ok(T)** -> it worked, here’s the value
- **Err(E)** -> it failed, here’s the error
If an error is not handled in Rust, the code does not compile.
```rust
let n: Result<i32, _> = "54".parse::<i32>();
```
- If the conversion succeeds: `Ok(54)`
- If it fails: `Err(...)`
---
## 00.13 Handling `.parse()`
Since `.parse()` returns a `Result`, you don’t know if it will return `Ok(T)` or `Err(E)`. That’s where `.unwrap()` comes in: if it’s `Ok(value)`, it gives you the `value`, but if it’s `Err(error)`, **the program crashes** (panic) and shows the panic message.
```rust
let x = "54".parse::<i32>().unwrap(); // x is i32
```
**When to use** `unwrap()`
- In examples and learning
- In quick prototypes
- When you are 100% sure it won’t fail
- In serious code, `match`, `expect`, or `?` are usually used (that comes later)
- If it can fail due to external input, don’t use `unwrap`
```rust
let x = "hello".parse::<i32>().unwrap(); // panic
```

## 00.14 Constants
Constants are permanently **immutable** and must have their type declared explicitly. They are evaluated at **compile time**. By convention, constant identifiers are written in UPPERCASE.
```rust
const SECONDS_IN_AN_HOUR: u32 = 60 * 60;
```
---
## 00.15 `let` vs `const` vs `static`
- `let` -> runtime variable
- `const` -> value known at compile time
- `static` -> global value with a fixed memory address, we’ll see it later
---
## 00.16 Naming conventions
- Variables -> `snake_case`
- Constants -> `UPPERCASE_WITH_UNDERSCORES`
- Avoid `x`, `y` except in examples
- Names that explain intent
---
## 00.17 Common mistakes
- forgetting `mut`
- trying to change the type with `mut`
- confusing shadowing with reassignment
- using `unwrap` without thinking
- trying to use a variable outside its scope
